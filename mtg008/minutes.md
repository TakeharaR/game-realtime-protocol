# AI エージェントを利用したネットワーク検証

資料 → [EM-uNetPi](https://github.com/KONAMI/EM-uNetPi)

### 背景

  * 運用型ゲームでは、リリース後もユーザ環境やインターネット全体の状況が変化する
    * 大規模配信
    * 大型タイトルの発売
    * 時間帯による混雑
    * 家庭内トラフィックの変化
  * ネットワーク検証には多くの課題がある
    * 遅延、パケットロス、帯域等のパラメータが多い
    * 網羅しようとするとテストパターンが増大する
    * パケット解析や障害切り分けには専門知識が必要
    * 検証担当者が属人化しやすい
  * リリース前の一時的な検証だけでなく、運用中の環境変化に追従できる継続的な検証が必要

### 発表内容

  * ``EM-uNetPi`` を MCP サーバとして扱い、OpenCode 等の AI エージェントから制御する
  * AI エージェントから次の操作を行える
    * 現在の設定値の取得
    * 遅延、パケットロス、帯域等の直接指定
    * 抽象的な通信環境を指定したパラメータ設定
    * 複数条件でのテスト実行
    * 結果の集計・レポート化
  * これにより、ネットワークに詳しくない開発者や QA 担当者でも検証を実行できる可能性がある
    * 検証手順の平準化
    * 人的コストの削減
    * ネットワーク検証の属人性低減

### 抽象的な条件指定について

  * 「特定地域のモバイル環境」等の指定値は、 ``EM-uNetPi`` 側に標準値として定義されているわけではない
    * 利用するモデルの事前学習内容と推定に依存する
    * モデルが変われば設定値も変わり得る
  * 検証根拠として扱うには、タイトルや実環境から収集したデータを参照させる必要がある
    * 中央値・平均値
    * 上位パーセンタイル
    * 地域・時間帯・回線種別ごとの分布
    * タイトル固有の通信パターン
  * 普段からログを収集し、検証へ利用できる形で整備することが重要

### 構成上の注意

  * AI エージェントと被試験ゲームクライアントを同一端末で動かすと、通信劣化設定が AI エージェント自身の通信にも影響する
    * 例えばパケットロスを 100% にすると、AI エージェントの外部接続も失われる
  * 実利用では次の経路を分離する必要がある
    * 被試験ゲームクライアントの通信
    * ``EM-uNetPi`` の管理・ MCP 制御
    * AI エージェントの外部接続
  * ゲームクライアントと AI エージェントを別端末にする構成が扱いやすい
  * この構成上の注意点はリポジトリのドキュメントへ追記する方向

### ゲーム通信の識別とデータ整備

  * キャリアや ISP からは、ゲーム通信の用途を区別しにくい
    * ゲームデータ
    * 更新・ダウンロード
    * リアルタイム対戦
  * QUIC 等で暗号化されると受動的な分類はさらに難しくなる
  * キャリア側の観測だけでは、どの通信条件をテストすべきか判断しにくい
  * ゲーム側のテレメトリや意味情報を組み合わせることが重要
  * ゲーム向けネットワーク環境のデータセットを共同で整備できると有用

### 今後の展開案

  * 実トラフィックデータに連動した試験条件の生成
  * CI/CD との統合
  * 継続試験と異常検知
  * タイトル固有条件での分析
  * エラー検出後のコード修正・再試験
  * 実環境データを用いたテストモデルの整備


# OSS RUDP / QUIC ライブラリ比較ベンチマーク

資料 → [rudp-bench](https://github.com/neguse/rudp-bench)

### 概要

  * OSS の UDP、RUDP、QUIC 系ライブラリを同一条件で比較するベンチマーク基盤
  * 同じ workload を与えた際の接続数、到達率、処理性能等を測定する
  * 主な試験モデル
    * Media Relay
      * クライアントから受信したデータを全クライアントへ配信する
      * 通信量が大きい条件
    * Game Server
      * 小さなデータを全クライアントへ配信する
      * 高頻度の Unreliable データと低頻度の Reliable データを混在させる
    * Echo
      * クライアントから受信したデータを当該クライアントへ返す
  * 到達率が一定値を下回った条件を限界として扱う
  * ENet、KCP、GameNetworkingSockets、LiteNetLib、MsQuic 等を比較対象としている
  * `apex_rudp` と `coop_rudp` は比較実験用の実装名
    * 既存のゲームタイトルとは無関係

### 現時点の結果の扱い

  * 現在の数値だけでライブラリの一般的な優劣は判断できない
  * 結果へ影響する要素が多い
    * 輻輳制御
    * 暗号化
    * 圧縮
    * ランタイム
    * 既定の接続数上限
    * OS・プラットフォーム
    * ベンチマーク側の実装方法
  * QUIC 系の結果が低い条件があっても、負荷モデルや輻輳制御との相性を含めて評価する必要がある
  * AI で生成・調整した実装は、ベンチマーク条件へ過剰適合している可能性がある

### 評価指標について

  * 接続数やスループットだけでは、ゲーム向けライブラリの評価として不十分
    * 送信を大きくまとめればスループットは上がる
    * その一方で、更新頻度や遅延が悪化し、ユーザ体験を損なう可能性がある
  * アプリケーション側から見た評価が必要
    * 画面上の動き
    * 操作感
    * 状態同期の滑らかさ
    * Reliable / Unreliable データの混在時の挙動
  * ライブラリ選定へ利用できる資料にするには、テスト結果をゲーム上の見え方やプレイ体験へ接続する必要がある
  * ゲーム特性ごとに複数の負荷モデルを用意する必要がある
  * 共通ベンチマーク基盤をコミュニティで整備すること自体に価値がある

### 対応ライブラリ・プラットフォーム

  * Adapter を追加することで対象ライブラリを増やせる
  * 実際の製品採用を考える場合は、数値以外の条件も必要
    * 利用可能なプラットフォーム
    * Unity 等からの利用可否
    * コンソール対応
    * NDA 下でのみ確認できる制約
  * 公開可能な範囲と、各社内で追加検証する範囲を分ける必要がある

# ゲーム業界のリアルタイム通信プロトコルにおける課題を洗い出す

### これまでの活動と現状

  * CEDEC 2023 のラウンドテーブルを起点として、ゲーム業界のリアルタイム通信プロトコルにおける課題を洗い出してきた
  * 当初は次の流れを想定していた
    1. ゲームにおける QUIC 採用事例を収集する
    2. 標準プロトコルと独自実装を比較する
    3. 不足があればゲーム向けプロトコルを提案する
  * しかし、公開された QUIC 採用事例が少なく、事例の増加を待つだけでは活動が進まない
  * 過去の会合では、プロトコル要素に限らず議論対象が広がっている
    * サンプル実装
    * 品質指標
    * 疎通性・到達性
    * 接続継続・復帰
    * 運用・観測
    * テスト環境
    * ユーザ体験

### 前回宿題: 「必要な要素」を「仕様」、「実装」、「環境」の分類別にまとめる

  * 第七回会合では、「疎通性」や「到達性」といった単一の語では表しにくい要素を、仮に「リアルタイム通信成立条件」として整理する方向になった
    * 通信経路の成立
    * 通信品質への適応
    * 接続の継続・復帰
    * データ転送モデル
    * 順序、期限、優先度
  * 第八回では、これらを「仕様」、「実装」、「環境」に分けて整理する作業について議論した
  * 宿題として分類を進めた結果、次の問題が明らかになった
    * 実装は仕様と環境から導かれる部分が多い
    * 「仕様」、「実装」、「環境」を同列に並べるだけでは関係性を表現しにくい
    * 要素数が多く、巨大なマトリクスは理解・維持が難しい
    * 下位のプロトコル要素から網羅的に積み上げると、議論が抽象化しやすい
  * 分類表を完成させること自体を目的にせず、整理方法を見直す必要がある

### プロトコル策定より先に要求・評価基準を整理する

  * 新しいプロトコルを先に作るのではなく、次の内容を整理する
    * ゲームが通信へ求める要求事項
    * 設計時に確認すべき観点
    * 選択肢ごとのトレードオフ
    * 評価指標
    * テスト条件
    * 実装・運用上の注意点
  * IETF の Requirements や Applicability に相当する文書のように、通信形態に応じた要求をまとめる方向が考えられる
    * RFC 化や標準化そのものを直ちに目的とはしない
  * AI にプロトコルや通信機能を実装させる場合にも、参照させる要求文書として利用できる
    * 実装生成のハードルは下がっている
    * その分、要求・前提・制約を正しく定義する重要性は増している

### 単一の正解ではなく、判断材料を示す

  * ゲーム業界の総意として単一の要件を定めることは難しい
    * 暗号化を必須とするか
    * 到達保証をどこまで求めるか
    * 遅延と信頼性のどちらを優先するか
    * Connection-Migration やマルチパスをどこまで使うか
  * 必須事項を一律に定めるのではなく、判断すべき観点とトレードオフを提示する
  * プロジェクトが必要な観点を選択し、優先順位を決められる資料を目指す

### ユースケースから要求を導く

  * 「ゲーム」という括りは広すぎる
  * 「格闘ゲーム」、「FPS」等のジャンルだけでも要件は一意に定まらない
    * 同じジャンルでも、到達性を優先するタイトルと即時性を優先するタイトルがある
    * ゲーム性や UX 上の要件によって、捨ててよいデータ、必ず届けるべきデータ、順序を守るべきデータが変わる
  * 下位レイヤーから網羅するのではなく、具体的なゲーム体験から上位・下位を往復して整理する
  * 想定する整理の流れ
    1. プレイヤーへ提供したい体験・ゲーム上の事象
    2. 必要な状態共有・合意・同期
    3. 通信上の要求事項と優先順位
    4. 適合するプロトコル特性・実装方針
    5. 試験条件・評価指標
  * タイトル名を公開できない場合でも、抽象化したゲームシチュエーションとして事例を収集する
    * 例: 特定ジャンル名だけでなく、「小さなキャラクターが多数同期する」、「少人数で厳密な入力同期を行う」、「一時的な欠落より遅延を嫌う」等の形で整理する
  * FPS、SRPG、対戦格闘等、参加者が経験を持つ具体的なケースを出すことで議論を地に足の着いたものにする

### UX・評価指標

  * ゲームネットワークには、業界共通の UX・QoE 指標が十分に整備されていない
  * プラットフォーム事業者の適合基準を満たすことと、良いユーザ体験であることは別
  * 遅延、ロス、更新頻度等を、プレイ体験へどのように結び付けて評価するかを整理する必要がある
  * EM-uNetPi や `rudp-bench` の成果を、ユースケースごとの要求・評価基準へ接続する

### 今後の方針

  * 当面は、新規プロトコルの標準化を直接のゴールとしない
  * ユースケース、要求事項、設計・評価ガイドラインの整理を優先する
  * 主幹が今回の議論を持ち帰り、資料構成と進め方を再整理する
